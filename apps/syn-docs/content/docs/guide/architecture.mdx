## Event Sourcing

Syntropic137 uses **event sourcing** as its core persistence pattern. Instead of storing current state, every state change is recorded as an immutable event. The current state is derived by replaying events.

<EventSourcingFlow />

### Two Event Types

Syntropic137 distinguishes between two kinds of events, each optimized for its use case:

| | Domain Events | Observability Events |
|---|---|---|
| **Purpose** | Business logic, state transitions | Telemetry, metrics, audit logs |
| **Storage** | TimescaleDB (append-only, replay-safe) | TimescaleDB (hypertable, time-series optimized) |
| **Pipeline** | Command → Aggregate → Event → Projection | Agent stdout → API stream processor → AgentEventStore → TimescaleDB |
| **Validation** | Aggregate invariants, can be rejected | Schema validation only, append-only |
| **Examples** | `WorkflowTemplateCreated`, `WorkflowExecutionStarted` | `tool_execution_started`, `token_usage` |

## CQRS

Commands and queries are strictly separated. Commands modify state through aggregates; queries read from pre-built projections stored in PostgreSQL.

**Commands:** `CreateWorkflowTemplateCommand`, `ExecuteWorkflowCommand`, `CancelExecutionCommand`, `ResumeExecutionCommand`, `RegisterTriggerCommand`, `PauseTriggerCommand`, `DeleteTriggerCommand`, and more.

**Events:** Every command produces one or more events: `WorkflowTemplateCreated`, `WorkflowExecutionStarted`, `ExecutionResumed`, `WorkflowCompleted`, `github.TriggerRegistered`, etc.

**Projections:** Pre-computed read models subscribed to domain events and stored in PostgreSQL. Includes a `repo_correlation` projection that maps repositories to workflow executions for cross-context insight queries.

## Real-Time Communication

Syntropic137 uses **Server-Sent Events (SSE)** for real-time monitoring of executions: progress updates, tool events, token metrics, and state changes all stream over a single connection:

```
GET /api/v1/sse/executions/{execution_id}
```

Global activity across all executions streams from `GET /api/v1/sse/activity`. From the CLI, `syn watch execution <id>` and `syn watch activity` follow the same streams.

Control commands are sent via standard REST API calls rather than a persistent connection.

**Cancel**: The platform checks for a cancel every few lines of agent output and interrupts the agent. Inject is accepted by the API but not yet delivered to the agent.

**Resume**: A `FAILED` or `INTERRUPTED` execution can be resumed, which creates a new execution. See [Resuming Failed Executions](/docs/guide/resuming-executions).

## Performance

Both event pipelines are optimized for their access patterns. Domain events use append-only writes with aggregate-level consistency. Observability events use TimescaleDB hypertables with automatic partitioning for high-throughput ingestion. Read models are stored in PostgreSQL.
