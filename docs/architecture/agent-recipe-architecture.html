Recipe

“What is this agent?”
agents/*.yamlmodel.name skillssubagents SYSTEM.mdsystem_instructions harnesstools enforced mcp policyskill pins evals/judges/ prompts/tools/ dir temperaturedescription
✕ task input✕ credentials✕ infra config
The recipe knows nothing above it. That is what makes it shareable — the same directory runs under any RunSpec, in any workflow, on any machine. Inline it into the RunSpec and every property below dies at once.

Consumer Flow

  1. Load — call load_recipe_dir(spec.recipe); never re-implement the shape
  2. Resolve entry — default_agent picks harness, model, resolved system prompt
  3. Resolve skills — refs → plugin dirs, order preserved
  4. Run — launch harness against the run's task

Consumer Must Not

  • Re-encode the recipe into a parallel schema
  • Read credentials or task input from the recipe
  • Inline the recipe instead of holding a path — the live Python bug: AgentRunSpec.recipe is an object, not a Path

Open Calls

  • Tool vocabulary — yours [bash, git, read] vs pi [read, write, bash]. Not portable yet.
  • pi branding — "pi" key and .pi/ dir: alias or rename
  • Model override — allowed, but evals must record the effective model

The Four Binding Seams

SeamRecipe declaresRunSpec binds
Toolsthe allowlist — an upper bound you can audit staticallymay narrow it further, never widen
MCPwhich methods are permitted per server (policy)endpoint + credentials for those servers (connection)
Skillsrefs and pins — source_url, version, resolved_shawhere they got materialized on disk
Harnessthe family — claude, codexthe execution path — interactive vs headless, tmux pane
Monotonicity rule. A RunSpec MUST NOT grant a tool or MCP method the recipe does not permit. Only then is the recipe's permission set a real ceiling — auditable on its own, without reading a single run.
