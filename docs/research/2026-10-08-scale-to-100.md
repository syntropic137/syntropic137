# What it takes to scale to 100, then 1,000 concurrent executions

Date: 2026-10-08. Status: research snapshot, docs only, no code changes.
Builds on epic [#1612](https://github.com/syntropic137/syntropic137/issues/1612)
and does not replace it. [north-star.md](../north-star.md) stays the living
capacity model; this file is a dated, conditional reading of it against the
2026-10-08 VPS observations. Checked against `main` at `25f4e2bbf`.

Scope: `sdlc-implement-v3` and `sdlc-reverify-pr-v1` workloads, on hosts of
16 cores and 62 GB. Every number in this file is conditional on that scope.

## Bottom line

1. **If today's single node and a comparable workload are kept, host CPU
   probably binds first at 20.** This is a hypothesis supported by the
   operator's report of the host CPU-bound at 10 (**measured**, 2026-10-08).
   The cap arithmetic, 10 workspaces x 2.0 CPU cap = 20 CPU > 16 cores
   (**scenario**; the 2.0 cap is a **code default**,
   `packages/syn-shared/src/syn_shared/settings/workspace.py:42`), shows only
   that the caps allow oversubscription: a cap is a ceiling, not demand
   (section 2). M3 settles it.
2. **If 100 is reached by scaling today's design, three blockers look
   structural rather than purchases:**
   placement across hosts ([#1734](https://github.com/syntropic137/syntropic137/issues/1734)),
   needed unless one node of 120-270 cores is chosen (**scenario**, section 2);
   executors split from the API (#1310 phase 1, the durable run queue);
   and provider quota, whose per-run cost is unmeasured
   ([#1718](https://github.com/syntropic137/syntropic137/issues/1718)).
   Whether quota is a purchase or a structural limit depends on the account
   decision in #1612 section 8 item 5.
3. **Every account count, host count and $/h figure here is a scenario**
   until measurements M0-M14 (section 4) land.
4. **On the 10-08 evidence, #1669 looks like the cheapest immediate step,
   and it buys diagnosis, not survival.** It captures the real Claude quota
   line so the failure classifies as `QUOTA` instead of `UNKNOWN`. `QUOTA` is
   not retried: it fails fast. Recognition then permits one attempt by the
   phase's `fallback_agent` only if one is declared, the primary did no work
   yet, and enough of the original phase deadline remains
   (`packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/busy_upstream.py:255-276`, called with
   `primary.got_somewhere` at `packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/agent_attempts.py:215-216`).
   Even then the fallback attempt can itself fail or run out of time, so
   survival is not promised. No workflow under `workflows/` declares a
   fallback today, and nothing in the code holds a run until a quota resets.
   So #1669 alone would not have held or saved the 4 runs killed at 08:11Z;
   they would still have failed, with an error naming the quota. Holding runs
   until reset belongs with per-provider budgets in the queue (#1718).
5. **On the evidence read here, #1612's design stands.** This file makes three refinements (see
   "Relation to #1612").

### Postgres connection arithmetic (scenario)

The API process builds five pools (**code default**, facts table): 20
(`agent_events`) + 10 (`subscription_checkpoints`) + 10 (`projections`) + 5
(`shared`) + 5 (`conversation_index`) = 50. The ESP event store connects to
the same TimescaleDB instance (`docker/docker-compose.syntropic137.yaml:76`)

- Today: 50 + 11 = 61, against the PostgreSQL default of 100 (no
  `max_connections` override exists in the repo outside `lib/`; deployment not
  read).
- Pessimistic scenario, 3 executors plus one API process, each with all five

- #1612 Step 4 plans otherwise: "The executor role gets only the observability
  pool ... and a small queue pool" (**from issue**). Under that plan the
  pessimistic case does not arise; the real number depends on the queue pool

## 2. Scenarios for 100 (no bounds claimed)

### Little's law

N = lambda x mean active duration D, so starts/h = N / D. The data gives
medians and p90s of completed runs, not means. The data establishes no
inequality between mean and median, and a p90 bounds nothing. Every row below
is a **scenario**, named by its assumption.

Population caveats:

1. The acceptance definition counts only executions with an agent actively
   working, not queued phases or idle slots (`docs/north-star.md:16`).
2. The measurement recipe uses admission-to-terminal wall time
   (`docs/north-star.md:63`).
3. Which of the two the supplied durations measure is unknown, and so is
   whether failed and incomplete runs were excluded.
4. Including in-phase waits (busy-upstream retries, gate queueing) inflates D
   for the "active" definition.
5. Excluding failed runs biases D in either direction.

M2 settles all five.

| Scenario | Assumption | starts/h = 100 / D | $/h = starts/h x $/run (API-equivalent) |
|---|---|---|---|
| implement-v3, median | mean D = 2 h | 50 (**scenario**) | 50 x $3-12 = $150-600 (**scenario**) |
| implement-v3, p90 | mean D = 3.3 h | 30.3 (**scenario**) | 30.3 x $3-12 = $91-364 (**scenario**) |
| reverify-pr-v1, median | mean D = 1 h | 100 (**scenario**) | 100 x $3-9 = $300-900 (**scenario**) |
| reverify-pr-v1, p90 | mean D = 4 h | 25 (**scenario**) | 25 x $3-9 = $75-225 (**scenario**) |
| Mix, 50 slots each, medians | D = 2 h and 1 h | 25 + 50 = 75 (**scenario**) | 25 x $3-12 + 50 x $3-9 = $75-300 + $150-450 = $225-750 (**scenario**) |

At 1,000 every row scales by 10, on the same assumptions. Pairing a duration
scenario with the full $/run range is itself an assumption: cost and duration
may be correlated.

**$/h is API-equivalent, not an invoice.** It is the current pricing table
applied to the current workload:

- on Claude Max it measures token volume, not cash;
- with API keys it is not guaranteed cash either, because the table does not
  model 1-hour Claude cache writes or the GPT long-context multipliers
  (`packages/syn-shared/src/syn_shared/pricing/__init__.py:204-205`,
  `packages/syn-shared/src/syn_shared/pricing/__init__.py:244-246`);
- billing mix and rate tier are unknown.

### Tokens per hour

Not derivable from the supplied data. The only points are the verify median
of 8.8M tokens (**from issue** #1726, one phase type) and one 25M-token run
(an anecdote quoted in #1726). 50 starts/h x 25M = 1.25B tokens/h is shown
**only as an illustration of scale, not an estimate of the mean.** The real
number comes from the four separate token categories in the rollup tables
(input, output, cache creation, cache read:
`packages/syn-adapters/src/syn_adapters/events/schema.py:276-316`), summed per
execution. Cache reads must be reported apart from input and output, because
their price and quota weight differ (M4).

### Provider accounts: formulas, not counts

For each provider window w (Claude 5 h session, Claude weekly, Claude
Opus-scoped weekly, Codex weekly):

- u_w = the fraction of window w consumed per occupied run-hour of the phases
  that use that provider;
- one account supplies 1.0 of window w per T_w hours;
- d_p = the share of run time spent in that provider's phases;
- accounts needed at N concurrent = max over w of (N x d_p x T_w x u_w) /
  (1 - headroom). The tightest window binds.

**Claude: no account count is given.** u_w is unmeasured for every window, and
one exhaustion event at one concurrency does not determine quota per run. The
18:30Z readings are data: weekly 86% left, session 73% left, Opus-scoped 0%
left. Opus-scoped at 0% bears directly on implement-v3, whose premise,
implement, fix and finalize phases run `opus`
(`workflows/sdlc/implement-v3/workflow.yaml:86`, `workflows/sdlc/implement-v3/workflow.yaml:111`, `workflows/sdlc/implement-v3/workflow.yaml:172`, `workflows/sdlc/implement-v3/workflow.yaml:315`; verify and reverify run `gpt-sol` at `workflows/sdlc/implement-v3/workflow.yaml:145` and `workflows/sdlc/implement-v3/workflow.yaml:209`). What Claude Code does
at Opus-scoped 0%, fail or fall back to another model, is unknown.

**Codex: a conditional scenario only.** Assumptions: the 4-10 concurrent runs
kept the Codex phases continuously occupied for 168 h; one account carried all
Codex work; the workload mix repeats. Then quota per concurrent run-week is
0.88 / N_avg, one account holds N_avg / 0.88 concurrent runs, and accounts at
100 = 100 x 0.88 / N_avg:

| N_avg | Accounts at 100 (scenario, 0% headroom) |
|---|---|
| 4 | 22 (**scenario**) |
| 7 | 12.6, so 13 (**scenario**) |
| 10 | 8.8, so 9 (**scenario**) |

If occupancy was intermittent, fewer run-hours consumed the same 88%, so more
accounts would be needed. The scenario is not a bound in either direction. M5
replaces it.

**API keys** raise request and token rate limits per organisation tier, not a
known amount of concurrency. The provider rate tiers were not read, and
request-rate demand is itself an estimate (0.03-0.1 req/s per Claude agent,
`docs/north-star.md:78`). "Buy keys" has no capacity figure yet (M6).

### Hosts of 16 cores (scenario)

Hosts at 100 = 100 x c / 16, plus a control-plane node.

| Per-run CPU c | Source | Hosts at 100 |
|---|---|---|
| 2.7 (**measured**) | load-average proxy, operator | 16.9, so 17 (**scenario**) |
| 2.0 (**code default**) | the cap; a ceiling, so "every run pegged at its cap" | 12.5, so 13 (**scenario**) |
| 1.2 (**estimate**) | north-star and #1714 (**from issue**), from #1600's gate observations | 7.5, so 8 (**scenario**) |
| 0.6 (**scenario**) | sensitivity: half of 1.2, for example after #1714 and #1726 | 3.75, so 4 (**scenario**) |

Hosts scale linearly with c. A single node would need 120-270 cores across
the first three rows (**scenario**). #1612 section 8 item 1 gives the host spec for 100 as
"about 8-10 × 16-core, 4-5 × 32-core, or 2-3 × 64-core (ESTIMATE)" (**from issue**), which matches the
1.2 row.

None of these is demand:

- load average counts runnable and throttled threads, and the control plane's
  share on the same host;
- workspace `cpu_usage_seconds` / wall measures CPU **delivered** on an already
  contended host, not unconstrained demand, and excludes the control plane;
- demand comes from a concurrency ramp that records CPU pressure, throttling
  (`cpu_throttled_seconds`, `nr_throttled`) and phase latency, as #1715
  specifies (M3).

The 2.7 proxy stays as one scenario.

## 3. Cheapest optimizations per run, by impact over effort

1. **#1669, the Claude quota line.** Cuts diagnosis waste, not CPU or tokens:
   the failure is named as `QUOTA` instead of `UNKNOWN`
   (`packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/upstream_failure.py:76-84`).
   A reset time is read only if the captured quota message contains one:
   #1669 asks for "a reset-time reader if a time is present" (**from issue**),
   so a usable reset timestamp is not guaranteed. Recognition can save a run
   only when the phase declares a `fallback_agent` (for example a codex
   fallback on the opus phases), the primary did no work yet, and the
   original phase deadline can still afford an attempt
   (`packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/busy_upstream.py:255-276`;
   caller `packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/agent_attempts.py:215-216`);
   even then the fallback attempt may fail. No workflow declares a fallback
   today. Smallest change.
2. **#1726, lean verify.** Cuts tokens and wall clock. Basis: verify median
   8.8M tokens (**from issue**). The reduction is not measured; the draft PR
   is OPEN.
3. **Base instruction size (proposed issue N3, measure first).** The
   duplicate import #1726 describes (AGENTS.md and CLAUDE.md byte-identical,
   "roughly 18k tokens loaded twice", **from issue**) is already removed on
   `main`: a byte-identical or breadcrumb AGENTS.md is no longer imported
   (`packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/handlers/instruction_imports.py:48-71`).
   What remains is the size of what is imported once: every phase gets the
   same synthetic `/workspace/AGENTS.md` and `/workspace/CLAUDE.md`
   (`packages/syn-domain/src/syn_domain/contexts/orchestration/slices/execute_workflow/handlers/WorkspaceProvisionHandler.py:562-581`),
   and this repo's `CLAUDE.md` is 37,276 bytes (**measured**, this checkout).
   #1726 reports 43,782 tokens of context on the first call of an Opus
   implement session (**from issue**). Whether a harness also loads a repo
   `CLAUDE.md` natively from its working directory is not shown by the code.
   No saving is claimed; N3 measures first-turn context per harness.
4. **#1714, warm dependency seed.** Cuts gate CPU and disk; five of six phases
   start cold (`docs/north-star.md:76`). Impact is an estimate. It is the main
   lever on c in the host table.
5. **#1715, budget from host capacity.** Cuts waste: oversubscription becomes
   queueing, not deadline failures. Needs M3.
6. **#1755, workspace directory reclaim.** Cuts disk. #1577 (disk health
   signal, admission floor, orphaned directory cleanup) is already merged;
   #1755 is the remaining step.
7. **#348, slimmer images.** Cuts pull time and disk.
8. **Model routing per phase** (which phases need Opus). Cuts tokens,
   Opus-scoped quota and $. #1718 covers per-provider budgets and quota
   telemetry but not routing; the routing question belongs to workflow
   experimentation and needs the M4 and M5 data first.

## Relation to #1612

No disagreement with the design. #1612: "one durable run queue (#1310 phase
1), with executors that are local Docker hosts or remote E2B accounts. The
claim is the placement decision, and a remote executor claims only when no
local slot is free" (**from issue**). Three refinements, each with evidence:

1. **Ranking.** After #1310 phase 1, provider quota and operator attention may
   bind before host count. Evidence: the 10-08 quota readings (4 runs killed,
   Opus-scoped 0%, Codex weekly 12%), presented as data, not account counts.
2. **Remote-tier gate.** For subscription (OAuth) credentials the gate is
   #1735 plus #1612 section 8 item 5 ("Model-provider account limits at 100
   and at 1,000 (Claude Max, Codex)"). Section 8 item 4, "Provider account
   ownership", concerns the E2B account only. #724 is the Claude API-key spike
   only: its body excludes OAuth (**from issue**).
3. **Stale citation.** #1612 Step 4 says to "make `max_connections(5)` and the
   30 s acquire timeout configurable", citing
   `lib/event-sourcing-platform/event-store/eventstore-backend-postgres/src/store_postgres.rs:203-212`,
   which on the pinned ESP is now unrelated event-metadata code. Both settings
   are already configurable: `PG_POOL_MAX_CONNECTIONS`, default 10, with
   an acquire timeout setting
   (`lib/event-sourcing-platform/event-store/eventstore-backend-postgres/src/config.rs:49-51`,
   `lib/event-sourcing-platform/event-store/eventstore-backend-postgres/src/config.rs:60`),
   applied at
   `lib/event-sourcing-platform/event-store/eventstore-backend-postgres/src/store_postgres.rs:394-396`,
   plus one listener connection
   (`lib/event-sourcing-platform/event-store/eventstore-backend-postgres/src/store_postgres.rs:245`).
   Connection growth across executors (Step 4) stands and is quantified above.
